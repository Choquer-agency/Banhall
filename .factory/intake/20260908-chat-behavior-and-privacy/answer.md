A large contiguous rewrite may fit, so bulk edits are not technically impossible; there is no first-class contract tying 16 distinct findings to coordinated edits and a post-edit completeness check. ## Proposed response contract

The assistant is an SR&ED writing collaborator. It should use authorized project evidence and the writer's effective settings, explain source-backed conclusions, and produce reviewable edits with minimal repetition from the writer. It should explain normal product workflows when appropriate, while protecting unauthorized client data, credentials, private prompts and internal configuration. Security must be enforced by server-side data/tool access and data minimization, with model instructions as one layer.

For a request to fix 16 listed deviations: keep all 16 in a revision checklist; map each to its source requirement and proposed change; prepare a coordinated revision against the current report revision; validate glossary, exclusions, evidence, applicable writing rules and line limits; report each item as resolved, blocked by specific missing evidence, or conflicting with an applicable rule. Preserve human approval through chatProposals/applyProposal. Do not ask the writer to invent wording already determined by their supplied instructions. Do not claim full compliance merely because a tool call succeeded.

The proposed contract does not amend product-domain policy. Existing confidentiality/readership, sharing, approved Brain usage and house-rule precedence must remain intact unless the owner explicitly changes them.

## Required proof before sign-off

- Replay a synthetic version of the incident with a settings document, exclusion list, confidence map, glossary, storyline, draft and 16 seeded deviations. Verify every corrected item and no invented facts; also verify rejection/refinement, partial application, stale report conflicts and long context.
- Exercise the actual model and tool layer with synthetic private canaries: direct and multi-turn prompt extraction, role spoofing, malicious attachment instructions, requests for another project's data and inappropriate shared-knowledge searches. Check responses and attempted tool calls; repeat across supported models/configurations. Structural tests remain necessary but insufficient.
- Inspect server authorization, shared-thread visibility, Brain source eligibility/redaction, response/trace/error exposure and configured provider data handling. Do not place credentials in model context. Model refusal cannot replace access control, and a finite red-team pass cannot guarantee no future disclosure.
- Confirm the effective settings/profile and complete inputs for the actual reported case before attributing its cause or claiming it fixed. Use authorized local fixtures; do not send client material to a new provider for testing without authorization.
