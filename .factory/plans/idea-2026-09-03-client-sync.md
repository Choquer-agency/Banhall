## A. Multiple transcripts per project

Today `transcripts` is one row per project (`convex/schema.ts` ~L487: `{ projectId, content, createdAt }`, `by_projectId`), `convex/transcripts.ts` exposes only `getTranscript(projectId)`, the new-project page (`src/routes/project/new/+page.svelte`, BNH-31) accepts exactly one .docx upload OR pasted text into a single `transcript` string, and generation (`convex/generations.ts` ~L362-455, ~L580, ~L801) reads one `generation.transcriptId`, slices content to 500 000 chars and records `truncated`. Reports carry `sourceTranscriptId` (`convex/reports.ts`, `reportProvenance`), and the Brain ingestion side (`convex/ingestion*.ts`) has its own `transcript` doc kind — do not touch ingestion.

Wanted:
1. A project can hold N transcripts (ordered, each with a file name / label and created time). Upload several .docx at once or one at a time; paste stays supported; remove one before generating. Keep the "review an existing PD from a project" prefill path (BNH-39 `sourceTranscriptId`) working — it should carry all transcripts of the source project.
2. Generation consumes all of a project's transcripts. Because the combined text can exceed what the model handles well (a single 2-hour transcript or several transcripts), add an explicit condensation step: when combined content exceeds a configured budget, reduce each transcript (or the concatenation) to a structured digest that preserves the SR&ED-relevant facts (who/what/when, technological uncertainties, hypotheses, experiments, results, dates, numbers, names) before it enters the existing prompt program; below the budget, pass the full text as today. The digest must be stored (so it is inspectable, provenance-linked and reused on regeneration) and the generation record must say whether it ran on full text or digests. Follow `docs/ai-architecture-plan.md` and `convex/ai/` conventions; use the existing model/gateway plumbing in `convex/ai/`; respect the "agents propose, humans apply" policy (this is generation input, not report prose mutation, so it is fine).
3. Provenance: reports/generations must reference the set of transcripts used (and digest ids when used), not a single `sourceTranscriptId`. Widen, don't break: keep `sourceTranscriptId` populated with the first transcript for old readers, add the list alongside. Schema changes follow the widen → backfill → dual read → narrow rule in `docs/product-domain.md`; this plan only widens.
4. Everything else that reads the single transcript (chat context, files panel, generation progress, snapshots, chronology agent, science-code suggestions — grep `transcriptId|getTranscript|sourceTranscriptId`) keeps working with N transcripts.
5. Tests at the Convex level for: multiple-transcript storage + ordering, generation input assembly below/above budget, digest persistence, provenance list, and back-compat for projects with the legacy single transcript. Component test for the multi-upload UI if `src/lib/components` is touched (`npm run test:component`, runs locally only).

Record a `docs/product-domain.md` amendment if any domain contract (transcript cardinality, provenance shape) changes — the policy requires it.

## C. Client uploader (Windows) finds zero documents on OneDrive

`scripts/client-uploader/banhall-uploader.ps1` (PowerShell 5.1, run via `Run-Uploader.bat`; Mac equivalent `banhall-uploader.sh`). On the client's Windows machine every mode (chooser, drag-drop, hand-typed `root`) prints `Found 0 document(s)` within ~10 s, for the full `Applications` folder and for small fully-synced client folders. Passed on the dev's Mac and Windows.

Primary hypothesis (verify, then fix): line ~211 drops any file whose attributes include `ReparsePoint`. OneDrive Files On-Demand marks every file under the sync root as a cloud reparse point (tags `IO_REPARSE_TAG_CLOUD*`), including files pinned "Always keep on this device"; macOS OneDrive uses File Provider, so the Mac script never sees it, and a Windows test outside a Files-On-Demand sync root passes. That check was meant to skip symlinks only. Fix: exclude only real links (`$_.LinkType` is `SymbolicLink`/`Junction`, or reparse points that are NOT cloud tags), keep cloud placeholders. Also:
- Dehydrated (cloud-only) files: `Get-FileHash` / `-InFile` will trigger a download per file — fine, but count them and tell the user up front (`N files are cloud-only and will be downloaded by OneDrive while uploading`), and treat a hydration failure as `READ_ERROR` (already handled) rather than a crash.
- Diagnostics (owner commitment in the meeting): when zero files are found, print and log a breakdown — total files walked, per-reason skip counts (extension, reparse/link, temp `~$`, dotfile, unreadable/access denied, cloud-only), the first few extensions seen, and whether the root is under a OneDrive sync root — so the next report is actionable. Write these lines to `upload-log.txt` too.
- Check the drag-drop and hand-typed-path modes for the same bug; the JSON `root` with double backslashes is correct, but make the error message explicit if the path does not exist or is a file.
- Keep the security posture (read-only, one endpoint, key only adds to queue) and the README/DEV-HANDOFF accurate.

Proof: `pwsh` is installed on this Mac (`/opt/homebrew/bin/pwsh`). Add a test harness (`scripts/client-uploader/tests/` or similar, run via `pwsh -File`) that exercises the file-collection logic against a temp tree containing: allowed + disallowed extensions, a `~$` temp file, a dotfile, a symlink (must be skipped), and a file with the ReparsePoint attribute set but no link target where the platform allows it (on macOS/pwsh simulate via a stub of the attribute filter — the filter should be factored into a function that takes the FileInfo so it can be unit-tested with a fake object). The gate must run this harness. Mirror the diagnostics in `banhall-uploader.sh`.
