# Agent DX and verification audit

Audited baseline: `11bfe3ebcb79fd8be78e2e057b45ea69db0f88be` on 2026-09-04. Read-only product/config audit. No shared server, deployment, customer data, or credentials were used. Relevant instructions: `.factory/AGENTS.factory.md`, `factory-principles`, `factory-verify-skill`, `principle-prove-it-works`, TypeScript best practices, and `convex/_generated/ai/guidelines.md`.

## Findings

### DX-1: Browser coverage is outside both automated gates (P1, source-verified)

The repo has **51 component test files** using actual Chromium and the production stylesheet. Neither CI (`.github/workflows/ci.yml:32`) nor the factory gate (`scripts/loop-verify.sh:19`) runs them. The factory QA minimum is `test-verified` and `qa.smoke` is empty (`.factory/factory.toml:22`). This lets a component regression pass every deterministic gate while relying on a human to remember the manual browser command. Separate Vitest configuration is appropriate and should remain; the missing automation is the issue.

Minimal fix: first reconcile the eight existing baseline failures below, then add an explicit browser verification job/command that installs the pinned Chromium browser and runs `npm run test:component`. Hook it into factory UI ticket verification and CI, or run it always if the measured duration is acceptable. Keep `npm test` browser-free as documented. Preserve the standalone component config without `sveltekit()`. Run that exact command from a fresh ticket worktree and retain the duration, failures, and screenshots. The current baseline failed in **50.988s: five files failed, 46 passed; eight tests failed, 281 passed**. Complete output is in `component-baseline.log` beside this report.

### DX-2: Fresh agents receive contradictory setup instructions (P2, source-verified)

`README.md:1` still calls this a Next.js app; lines 17 and 19 send readers to port 3000 and `app/page.tsx`. Actual scripts use SvelteKit/Vite on 3001 (`package.json:7`, `vite.config.ts:9`). No tracked environment template or Node version file exists. `docs/bmad-loop.md:54` instructs in-place work and says dependencies prevent worktrees, while `scripts/loop-verify.sh:14` now installs dependencies in empty worktrees and `.factory/AGENTS.factory.md:6` mandates factory worktrees. `docs/bmad-loop.md:65` also tells agents to create a second worktree and copy `.env.local`; `docs/svelte-migration.md:87` points them to the shared server. These are active command recipes, not merely historical architecture notes.

Minimal fix: replace the scaffold README with current setup and one canonical verification entry point. Mark the legacy orchestration and migration-era verification instructions historical, and point to current factory instructions. Document npm as the lockfile-backed verification path, Node version, PowerShell requirement for uploader checks, Chromium setup, dummy `PUBLIC_CONVEX_URL` for typechecking, and the different requirements for running the real app. Do not copy a shared environment into a verification instance.

Useful doctor checks: required binaries, dependency resolution, Chromium executable existence, checked-out worktree identity, requested port availability, and presence of required env **names** without printing values. Fail fast before expensive checks when a required tool is missing. The current `loop-verify.sh` checks dependency-directory emptiness, not dependency integrity, then discovers missing `pwsh` only after all TypeScript/unit work; this is a portability weakness, not a reproduced failure on this host.

### DX-3: No maintained path proves a complete user flow against a private app instance (P1 capability gap, source-verified)

`.factory/verify/` does not exist; there are no launch/doctor/drive/cleanup helpers or feature map. No tracked Playwright E2E configuration is present. Browser suites alias auth, Convex, navigation, and env modules (`vitest.component.config.ts:29`), so they prove component behavior but cannot prove cookie exchange, real route loading, Convex subscriptions, and persisted writes together. This is an honest coverage boundary, not a reason to delete component tests.

A fresh private backend also cannot reuse `seedDemoProject` unattended: it first needs a pre-existing demo user (`convex/seed.ts:51`), and signups require invitations (`convex/auth.ts:40`). The frontend's auth route proxies to the selected Convex HTTP endpoint (`src/routes/api/auth/[...all]/+server.ts:1`). A browser-only preview with placeholder env cannot prove authenticated application behavior.

Minimal useful increment: create `.factory/verify/SKILL.md` and helpers for a disposable instance, with explicit Launch / Doctor / Drive / Evidence / Cleanup sections and a small feature map. First prove a local frontend route or the self-contained uploader path, and label that proof's limited scope accurately. Full login -> create project -> upload -> observe persisted result needs an isolated Convex backend and seeded invitation/account owned by that run. Restrict external AI calls at their existing provider boundary. Refuse shared endpoints instead of silently falling back to `.env.local`. Mark authenticated end-to-end coverage draft until those dependencies and the live pass exist.

Port isolation belongs in the harness: launch on an explicit port with `--strictPort`, record the owning process and instance identity, assert the backend endpoint belongs to that run, and stop only that process. The app hardcodes trusted local auth origin 3001 (`convex/auth.ts:21`), while Vite has no strict-port setting (`vite.config.ts:8`); a worktree on another port requires a matching trusted origin in its private backend configuration. This mismatch is source-verified; no shared-server collision or remote auth request was attempted.

### DX-4: Automated coverage has a known unowned test directory (P2, discovery-verified)

`npx vitest list --filesOnly --json` discovers **128 files**: 80 Convex-project files, 42 src, five shared, one source audit. The `tests/` directory contains 15 suites; only `tests/aiUsage.test.ts` is included. The other 14 Bun suites are outside every npm/factory/CI test path (`vitest.config.ts:29`). This is already acknowledged in `docs/system-map.md:414`; do not present it as a new regression.

Minimal fix: let the slop audit classify these suites, port unique behavior coverage into maintained Vitest suites, and delete only the obsolete or fully redundant harnesses. Add a lightweight discovery assertion that every tracked test belongs to one supported runner (or an explicit documented exception). Do not add Bun to the gate just to keep stale mock DB implementations alive. The slop agent independently ran the legacy suites and owns the detailed failure/equivalence analysis in `slop-audit.md`.

## Suggested delivery order

1. Fix the canonical setup/verification entry point and missing browser gate, using the current baseline to separate pre-existing failures from changes. This is the smallest high-value DX ticket.
2. Migrate useful orphan tests as a separate slop ticket with old failure/new success evidence.
3. Build and prove the private app verification harness as its own ticket, with backend/account isolation explicit in acceptance criteria. A README describing a never-run harness is not a completed verifier.

Principles changing these recommendations: **Build the lever** favors executable doctor/drive commands over more prose; **Laziness protocol** reuses current component and uploader harnesses; **Prove it works** keeps component proof separate from end-to-end proof; **Separate before serializing shared state** requires private instances rather than a lock around port 3001 or the shared deployment.

## Disposable backend/auth feasibility follow-up

**A local harness needing no pre-existing cloud credentials is viable.** This is based on installed Convex **1.42.3** source and successful read-only CLI/binary help commands, not a backend launch. No account, deployment, env file, or database was changed in this follow-up. Authenticated E2E should therefore be scoped as implementable tooling work, not deferred merely because the current app normally uses a cloud backend.

- **Backend isolation already exists upstream.** `node_modules/convex/src/cli/lib/localDeployment/anonymous.ts:318` supports `CONVEX_AGENT_MODE=anonymous` without cloud project registration. State defaults to `.convex/local/default/` per worktree (`filePaths.ts:12`); `secrets.ts:45` generates local instance/admin credentials. `dev.ts:162` has explicit local cloud/site port flags, and `utils.ts:26` rejects occupied requested ports. However anonymous mode is not a protection against shared config: `deploymentSelection.ts:573` loads `.env.local` and process selector variables before deciding anonymous mode, and `anonymous.ts:281` reuses existing project-local state. Its file-path resolver can also reuse legacy home state for a matching deployment name. A launcher must prevent all three fallbacks.
- **The direct binary is a simpler strict-isolation option.** The cached executable `/Users/johnnynguyen/.cache/convex/binaries/precompiled-2026-08-25-7cce8fb/convex-local-backend --help` exited 0. It supports `--interface 127.0.0.1`, distinct `--port`/`--site-proxy-port`, explicit `--instance-name`, `--instance-secret`, `--local-storage`, a SQLite path positional argument, `--disable-beacon`, and `keygen` without starting a server. A harness can own every mutable path beneath its run directory and pin/configure the executable version. A fresh host needs this public binary download, not an account. Subsequent CLI operations can use a private `--env-file` containing only that instance's `CONVEX_SELF_HOSTED_URL` and generated `CONVEX_SELF_HOSTED_ADMIN_KEY`; the selector code rejects an incomplete explicit env file instead of consulting shared selectors (`deploymentSelection.ts:541`). These options were read, not run.
- **Auth requires local configuration and fixture data, not OAuth or email credentials.** Configure a newly generated `BETTER_AUTH_SECRET`, local `SITE_URL`, and the chosen frontend origin in `BETTER_AUTH_TRUSTED_ORIGINS`. Give Vite matching `PUBLIC_CONVEX_URL`/`PUBLIC_CONVEX_SITE_URL` and `--strictPort`. Banhall uses password auth with email verification disabled (`convex/auth.ts:113`); Better Auth's Convex plugin generates and stores signing keys locally (`node_modules/@convex-dev/better-auth/src/plugins/convex/index.ts:202`). The local backend exposes its own HTTP/JWKS origin. The remaining live proof is browser signup/signin, cookie exchange, and authenticated subscription against that origin.
- **Seed the invitation through the isolated administrative boundary, then drive real signup.** Existing `convex import --table` supports JSON arrays, and `convex run --inline-query` supports a read-only second view. Import a synthetic inviter user into the empty local database, read its generated ID, and import a pending invitation referring to that ID with a generated token and future expiry (`convex/schema.ts:43`). Drive `/signup/<token>` through normal browser form actions. Both invitation checks and the Better Auth user-created trigger then run unchanged (`convex/invites.ts:169`, `convex/auth.ts:40`). No new auth bypass, production seed function, or known shared user's credentials are needed. A normal admin account can create further invites through the real app after this bootstrap.
- **Keep the AI boundary explicit.** All external AI/API keys in `convex/convex.config.ts` are optional, so auth/navigation/data flows need no provider secrets. Successful generation is a separate boundary: the normal New project wizard calls `requestGeneration` (`src/routes/project/new/+page.svelte:765`). A secret-free success test must provide a deterministic provider fixture through an approved existing boundary; absent that, prove the actual missing-provider failure/recovery path and label it accordingly. The existing duplicate-project branch avoids starting generation (`:762`) and can prove project creation/copy with a synthetic source fixture. Do not claim a generated report merely because a fixture was imported.

Concrete missing deliverables: owned backend/frontend process launcher with private paths and endpoint assertion; pinned/public binary setup; local env provisioning; finite user/invite fixtures; browser signup/login and one persisted-data journey; read-only DB evidence; screenshots/logs with credentials redacted; cleanup that preserves evidence. The cached binary runs on this host, but backend startup, function push, Better Auth handshake, seed import, and browser drive still require an actual end-to-end proof. This clarifies DX-3: the current harness is absent, but shared credentials are not an inherent blocker.
