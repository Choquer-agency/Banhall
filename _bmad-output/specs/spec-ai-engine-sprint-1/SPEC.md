# AI engine sprint 1: close the boundary

## Why

A pain to solve and a mandate to meet. The 2026-08-25 audit found that callers without a valid internal role, including unauthenticated and role-less users, can mutate report prose; that two proposal-apply paths skip the snapshot and revision safeguards; and that neither cost nor prompt/digest version can be attributed to a generation. These are the cheapest, highest-leverage gaps before the Phase 2 trusted-context work in `docs/ai-architecture-plan.md`. Each is a small change with a deterministic test. This rewrite (2026-08-28) makes the contract self-contained: normative acceptance behavior lives here and in `stories.yaml`; `touchpoints.md` carries file anchors and verification targets.

**Evidence status.** This contract was produced from BMAD artifacts and the audit document only. No source code, git history, tests, or external docs were inspected in this pass. Every claim below about a function name, file line, role enum, public API surface, Convex limit, retry behaviour, or test file is **UNVERIFIED** and must be confirmed by the planning step before implementation (see "Planning verification gates"). Behavior stated as acceptance criteria is normative regardless of how the code is currently shaped.

## Capabilities

- **CAP-1** Internal role gate on project-scoped access
  - **intent:** Only a signed-in user holding an internal role can use paths guarded by `requireInternalProjectAccess`; anonymous and role-less identities are refused. Scope is exact, not universal: every current direct or transitive helper caller inherits the tightened rule, including 60 public mutations, four privileged public queries, and two public project-copy/review actions inventoried at gate G-11. Dashboard reads guarded only by `requireCurrentUser` and client share-token flows are unchanged.
  - **success:** (a) Helper parity has direct unit coverage: `requireInternalProjectAccess` and `getInternalProjectAccessOrNull` decide identically for the same identity across no/unmapped identity, stored anonymous, signed-in role-less, and signed-in internal-role cases. (b) `updateReportContent` and `applyProposal` are representative write integrations, with owner or elevated positive controls and complete no-write assertions after rejection. (c) `listMessages`, `getReadiness`, `preflightExport`, `getMyQaItemFeedback`, `copyProjectContent`, and `createReviewFromProject` smoke-test the approved query/action blast radius. (d) The complete G-11 inventory is recorded in the Story 1 companion notes, and every inventoried write path is confirmed to reach the guard before its first write.

- **CAP-2** Proposal apply parity on both public paths
  - **intent:** Every proposal that reaches `applied` did so through a transaction that rechecked authorization, snapshotted the pre-edit content, fenced on the report revision, wrote the content and the status atomically, and bumped the revision; the one-by-one path (`markProposalApplied`) offers exactly the same guarantees as `applyProposal`.
  - **success:** After a one-by-one apply from `ProposalCard.svelte`: the proposal is `applied`, a `pre_chat_edit` snapshot exists whose content equals the report content immediately before that apply, and `revisionNumber` increased by exactly one. A second call with the same `expectedRevisionNumber` is rejected with a typed stale-revision error and leaves proposal status, content, revision, and snapshot count unchanged. There is no reachable sequence of public calls that yields an `applied` proposal without the matching snapshot and bump. The public path `markProposalApplied` remains; the one-by-one UX in `ProposalCard.svelte` is preserved (see Decisions D-1).

- **CAP-3** Publish-for-review by role, not by creator
  - **intent:** Publishing a report for client review is authorized by the caller's current role on the project (Owner, Manager, or Admin), never by `projects.createdBy`.
  - **success:** After ownership transfer, the new Owner and a Manager can call `publishForReview`; the original creator, who now holds none of Owner, Manager, or Admin on that project, is rejected; a signed-in internal user whose current project role is one G-1 identifies as ineligible (any internal role other than Owner, Manager, Admin; if G-1 finds no such role exists, record that and drop this case) is rejected; an anonymous caller is rejected. No write occurs on rejection (project status and report fields unchanged). Recorded decision D-2.

- **CAP-4** Reversible client-edit acceptance and post-persist Brain nomination
  - **intent:** Accepting a client's suggested edit is reversible through a snapshot, and a writer review is only nominated to the Brain once its row is persisted.
  - **success:** (a) `acceptEdit` writes a snapshot of the report content in the same transaction, before patching; restoring that snapshot returns the exact pre-accept text. (b) `submitWriterReview` (nomination site in `convex/reviews.ts`) enqueues Brain nomination only after the `writerReviews` row is written and passes that row's id; when the insert fails (validation or thrown error) no nomination is scheduled and no `writerReviews` row exists. Split into two stories (4, 5).

- **CAP-5** Brain feedback scoped to accessible report and project
  - **intent:** Writer feedback to the Brain can only reference a report and project the caller can access, and the two must belong together.
  - **success:** `submitBrainFeedback` rejects, before any write, each of: a `reportId` the caller cannot read; a `projectId` the caller cannot access; a `reportId` whose `projectId` differs from the supplied `projectId`; a caller without an internal role (via CAP-1 helper). An internal-role caller with a matching, accessible pair succeeds (positive control).

- **CAP-6** Provider retry budget fits the owning action
  - **intent:** The worst-case wall time of the Anthropic provider path used by `generateCandidate` (all attempts of every sequential provider call inside that action, plus a named reserve for retry backoff and the rest of the action's work) fits inside the Convex action limit. The normative requirement is the budget inequality; specific numbers are targets that hold only when planning confirms the inputs.
  - **success:** The provider module exports `timeoutMs`, `maxRetries`, `sequentialCallsPerGenerateCandidate` (`calls`), `reservedNonRequestMs`, and `actionLimitMs` as named constants. `reservedNonRequestMs` is a conservative, named reserve covering the maximum retry backoff the SDK can add plus all remaining non-request action work; it is at least `60 000` ms unless source evidence recorded at planning justifies another number. A deterministic test imports the actual configuration (not literals copied into the test) and asserts `calls * (maxRetries + 1) * timeoutMs + reservedNonRequestMs < actionLimitMs`. The test always asserts `maxRetries === 1`. It asserts `timeoutMs === 240000` only when `calls === 1` and the verified `actionLimitMs` (G-5) and `reservedNonRequestMs` make that value satisfy the inequality; if planning finds more than one sequential call, a smaller limit, or a larger required reserve, `timeoutMs` is lowered until the inequality holds and the exact-value assertion tracks the lowered value. Target configuration under Assumption A-2: `maxRetries: 1`, `timeoutMs: 240000`, `calls: 1`, `reservedNonRequestMs: 60000`, `actionLimitMs: 600000`. Scope is the Anthropic client in `convex/ai/providers.ts` and the `generateCandidate` action; other clients are in scope only if planning verifies they run under the same action budget.

- **CAP-7** Superseded generations and QA gated on report existence
  - **intent:** A generation whose failed candidates were retried is marked `superseded`, is excluded from history and stats, and QA cannot be requested on any generation that has no report.
  - **success:** After `retryFailedCandidates`, the original generation has status `superseded` (new union value, Assumption A-1) and the new generation is the one that continues; history and stats readers exclude `superseded` (not counted as completed, failed, or in progress); `retryFailedCandidates` on an already `superseded` generation is rejected. `requestReportQa` on a generation with no report (including `superseded`) returns a typed error (`ConvexError` with a stable `code` field) and writes nothing.

- **CAP-8** Bounded chat context, bounded proposal lists, safe empty reads
  - **intent:** Chat history sent to the model is capped, `listProposals` never returns proposals outside the turn window the client has loaded, and reading a nonexistent or deleted thread renders empty instead of erroring, while an unauthorized read of an existing thread still errors.
  - **success:** (a) The context passed to the model is at most 30 recent messages with tool messages excluded; verified by asserting the context options constant used by the `streamText` call and, if the agent library allows, by a thread of 35 messages including 5 tool messages yielding ≤ 30 non-tool messages. (b) `listProposals` accepts the same optional window arguments as `listTurns` (default window identical) and returns only proposals whose turn is in that window; a proposal on a turn outside the window is absent. (c) `listMessages` and `listProposals` return `[]` when the thread does not exist or is deleted; when the thread exists but the caller is not authorized, the existing authorization error is thrown (not `[]`). Existing callers keep an unchanged call shape (no new required arguments; source compatibility preserved); their results are intentionally bounded by the default `listTurns` window and may therefore omit proposals on turns outside that window, which is the point of the change, not a regression.

- **CAP-9** Generation provenance and recorded attributable cost (post-deployment generations)
  - **intent:** Every generation created after this change records a deterministic hash of the prompt program that produced it and the deduplicated set of learning digests whose content was actually sent to the provider for it, and its recorded provider usage is attributable through `aiUsage` rows keyed by generation.
  - **success:** For a generation created after deployment, `getGeneration` returns: `promptVersion`, a deterministic hash of the stable prompt program (static system templates, instructions, and relevant prompt configuration; excludes runtime project, report, transcript, and digest content) such that the same prompt program yields the same hash across runs and generations; `learningDigestIds`, the deduplicated union of digest ids whose content was included in any provider request payload for that generation, recorded or updated immediately before each payload is handed to the provider SDK, allowed to grow during a multi-call generation, and final once the generation reaches a terminal status (a digest that was fetched but not included in any payload is not listed; empty array when none); and `cost`, defined strictly as the sum of recorded `aiUsage` cost rows with matching `generationId`, in the cost unit already stored on `aiUsage` (planning verifies field and unit). `cost` documents recorded attributable cost, not invoice completeness: every provider call that returns usage writes a row, including calls whose generation later fails, times out after usage, or is retried; calls that return no usage have no row and contribute nothing. For a legacy generation (no `promptVersion`), `promptVersion`, `learningDigestIds`, and `cost` are `null` (unavailable), never `0`. `cost` is `0` only for a tracked generation with no usage rows yet. Any caller authorized to read the generation sees these fields; an Admin can read them for any generation. Split into two stories (10, 11); full semantics in "Decisions D-4".

- **CAP-10** Confirmed Brain unlearn, evidence on failure, no retries against revoked sources
  - **intent:** Revoking a Brain source records `unlearn_confirmed` only when remote erasure is confirmed or the entry is already absent, keeps evidence when erasure fails, is idempotent on repeat, and no queued or late embedding work can restore a revoked source, leave an orphaned remote entry unaccounted for, or trigger retries.
  - **success:** (a) Revoke with a live `ragEntryId` and confirmed erasure: one `unlearn_confirmed` audit row, `ragEntryId` cleared, source not approved. (b) Revoke where the remote reports the entry already absent, or the source never had a `ragEntryId`: same outcome as (a). (c) Revoke where erasure fails: no `unlearn_confirmed` row, `ragEntryId` retained, source not approved (not servable), failure surfaced to the caller and recorded as evidence (existing audit action if one fits, else optional new `unlearn_failed` value). (d) Second revoke after (a): returns without error, makes no remote call, writes no second `unlearn_confirmed` row. (e) `embedSource` on a source that is missing, revoked, or otherwise not approved returns normally without throwing, writes no `ragEntryId`, and schedules no retry. (f) Embedding that completes remotely after revoke: the source is not approved, the entry is not served, and embedding is not retried. The completion path performs compensating erasure of the newly created remote entry. If compensation confirms deletion or already-absent, `ragEntryId` is not written and status is unchanged. If compensation fails, the remote id is retained as evidence (in `ragEntryId`, or in an additive evidence field if planning finds `ragEntryId` unsuitable; see Constraints), the source stays non-approved and non-servable, failure evidence is recorded (same mechanism as (c)), and deletion-only remediation is scheduled or surfaced to an operator; no embedding retry is scheduled. `unlearn_confirmed` is never written for that late entry until compensation is confirmed. The late-completion fence in `convex/ai/brain/rag.ts` is the pattern to mirror for the status check. Remote API details are not specified here; planning verifies (G-8) what "confirmed" and "already absent" look like for the actual RAG client and what deletion call the compensation path uses.

- **CAP-11** Reaper covers every eligible project, bounded per transaction
  - **intent:** The stale-generation reaper reaches every project in an eligible status via an index, in bounded pages, without an unbounded transaction and without a fixed cap.
  - **success:** `projects` gains an index on `status`; the reaper walks eligible statuses with cursor or last-key continuation at a fixed page size, each page in its own bounded transaction, until exhausted. Deterministic test: seed more than 500 eligible projects each with a stale generation (or seed a small set with the page size overridden below the seed count) and assert every stale generation is reaped, projects in non-eligible statuses are untouched, and no single transaction reads more than one page. `take(500)` is gone.

## Decisions

- **D-1 (CAP-2):** Keep `markProposalApplied` as a public path. It must, inside one mutation: recheck project authorization with the CAP-1 helper; require `expectedRevisionNumber` and reject with a typed stale-revision error when it differs from the report's current `revisionNumber`; write a `pre_chat_edit` snapshot of the content as it stands before this proposal's edit; write the new content; increment `revisionNumber` by one; set the proposal to `applied`. If today's `markProposalApplied` only flips status while the client writes content separately, the content write for that proposal must move inside it so no window exists where content changes without a snapshot. Sharing an internal helper with `applyProposal` is allowed, not required. `ProposalCard.svelte` supplies `expectedRevisionNumber` and surfaces the stale error without crashing; the one-by-one UX is otherwise unchanged. Implementation choice is not left to dev.
- **D-2 (CAP-3):** Current Owner, Manager, and Admin on the project may publish for review. The original creator is denied once they no longer hold one of those roles on that project. `projects.createdBy` is not consulted for this decision (policy: never repurpose `createdBy`).
- **D-3 (schema):** Additive only; the complete allowed set is in Constraints. No backfill, no migration, no field renames.
- **D-4 (CAP-9 semantics):**
  - *Tracked generation* = `promptVersion` present. Provenance and cost guarantees apply only to tracked generations; legacy rows expose `null` for all three fields.
  - `promptVersion` = deterministic hash of the stable prompt program/definition used by the generation: static system templates, instructions, and relevant prompt configuration (model routing, structured-output schema, and similar settings that change what the prompt asks for). It excludes runtime content: project data, report text, transcript, digest content, and per-call user messages. Same prompt program yields the same hash across runs and across generations; any change to the program changes the hash. Algorithm and the exact list of hashed inputs are chosen at planning and recorded. Written when the generation record is created or, if the program is only resolved later, before the first provider call for that generation.
  - `learningDigestIds` = the deduplicated union of digest ids whose content is included in any provider request payload for that generation. The union is recorded or updated immediately before each payload is handed to the provider SDK (the assembly sites in `pipeline.ts` and `iterative.ts` are the expected anchors); it may grow during a multi-call generation and is final when the generation reaches a terminal status. Fetching a digest without including it in a payload does not count. Empty array when no digest content was sent; `null` only for legacy generations.
  - `aiUsage` rows gain optional `generationId`, `candidateRunId`, `durationMs` and an index on `generationId`. Instrumentation writes a row for every provider call that returns usage on behalf of a generation, including calls whose generation later fails or is retried. Calls that return no usage (aborted before the provider responded, transport failure) have no row; no synthetic zero-token rows are written.
  - `cost` = sum of recorded `aiUsage` cost rows with matching `generationId`, computed in `getGeneration` via the index; the number of rows per generation is bounded by the pipeline's call count (planning confirms it is small enough for a single query). While a generation is in flight, `cost` reflects rows written so far. `cost` is a statement of recorded attributable cost, not a claim of exact total provider spend or invoice completeness; documentation on the field says so.
  - Visibility follows the existing `getGeneration` authorization (internal role after CAP-1); no separate gate.
- **D-5 (CAP-8 window):** "Loaded turn window" is the set of turns `listTurns` returns for the same thread and the same optional window arguments. `listProposals` mirrors those arguments; defaults are identical.
- **D-6 (CAP-11 eligibility):** Eligible statuses are those the current reaper already treats as candidates; planning enumerates them from source. Page size is a named constant, overridable in tests.

## Constraints

- Agents propose, humans apply (`AGENTS.md` policy): no fix may add a code path where an AI tool writes report prose; all prose changes stay on `chatProposals` + apply mutations.
- Public `api.*` function paths stay stable. New arguments are optional, except `markProposalApplied.expectedRevisionNumber`, which is required by D-1 and whose only known caller is `ProposalCard.svelte`. Frontend behavior is unchanged; the only frontend file edited is `src/lib/components/chat/ProposalCard.svelte`.
- Schema changes are additive only. Allowed set: `generations.status` adds `superseded`; `generations` adds optional `promptVersion` (string) and `learningDigestIds` (array of digest ids); `aiUsage` adds optional `generationId`, `candidateRunId`, `durationMs` and index `by_generationId`; `brainAuditLog` action union adds `unlearn_confirmed`; `projects` adds an index on `status`. Optional, planning-gated additions: `generations.supersededBy` (id, only if a consumer needs the link), a new snapshot kind for CAP-4 if no existing kind fits, `brainAuditLog` action `unlearn_failed` if no existing action records failed erasure; one additive optional evidence field on the Brain source row (for example `orphanedRagEntryId`, name at planning) holding the remote id of a late-embed entry whose compensating deletion failed, only if planning finds `ragEntryId` unsuitable as the evidence carrier for CAP-10(f). Nothing else. Index names follow the existing `by_*` convention in `convex/schema.ts`.
- No backfill: legacy generations and usage rows are never rewritten; readers must tolerate absent fields.
- All `convex/` edits follow `convex/_generated/ai/guidelines.md`.
- Rejections in CAP-1, CAP-3, CAP-5, CAP-7 occur before any write in the same function.

## Success signal

An unauthorized caller cannot change report prose, every human-applied proposal and accepted client edit is reversible, every post-deployment generation exposes its prompt provenance and recorded attributable cost, revoked Brain sources cannot be restored by queued work, and stale-generation recovery covers every eligible project.

## Exit criteria

Baseline status of `npm test` is unknown: it was not run in this artifact-only pass and no green baseline is claimed. The sprint exits when `npm test` is green on the final integrated branch and includes deterministic tests for every capability as listed in `touchpoints.md`: CAP-1 helper parity plus representative anonymous, role-less, and authorized cases with no-write assertions; CAP-2 parity plus stale-revision; CAP-3 role matrix including the ineligible internal role; CAP-4 restore and no-nomination-on-failure; CAP-5 four rejections; CAP-6 budget inequality over imported config; CAP-7 superseded and typed QA error; CAP-8 window and empty-vs-unauthorized; CAP-9 prompt-program hash stability, payload-derived digest union, recorded-cost sum, and legacy null; CAP-10 six revoke/embed cases including compensating erasure on late embed; CAP-11 over-500 or bounded-page reaping. ## Assumptions

- **A-1:** `superseded` is a new value in the `generations.status` union rather than a boolean flag.
- **A-2:** A 4-minute provider timeout (`timeoutMs: 240000`) with `maxRetries: 1` is acceptable for the largest transcripts, `generateCandidate` makes one sequential provider call per action, and a `reservedNonRequestMs` of `60 000` covers maximum SDK retry backoff plus remaining action work. Under those inputs `1 * 2 * 240000 + 60000 = 540000 < 600000` holds. If planning finds more sequential calls, a larger required reserve, or a smaller action limit, `timeoutMs` shrinks so the CAP-6 inequality still holds and the exact-value assertion moves with it.
- **A-3:** `promptVersion` is a hash, not a semantic version string (memlog decision preserved).
- **A-4:** The Convex action limit relevant to CAP-6 is 10 minutes (`actionLimitMs: 600000`); unverified here and confirmed at G-5 before the CAP-6 constants are fixed.
- **A-5:** `ProposalCard.svelte` has, or can cheaply obtain, the report's current `revisionNumber` to pass as `expectedRevisionNumber`.
