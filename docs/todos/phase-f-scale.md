## F1. Request size from the token count endpoint

**Today.** Every evidence budget turns tokens into characters at 4 characters a token (`CHARS_PER_TOKEN`, `convex/ai/trustedContext.ts`), used by drafting and analysis (`buildTrustedContext`), the Brief request (`briefRequest.ts`), chat evidence (`chatEvidence.ts`) and the review agent. Brief preparation reserves rate-limit room at 3 characters a token. Nothing measures how far off that is. SR&ED evidence is dense with numbers, units and names, which cost more tokens per character than plain prose, so a request can be larger than its budget says.

**Change.**
1. **Measure every request.** The instrumented client (`convex/ai/instrument.ts`) already records each call's actual input tokens on its `aiUsage` row; it will also record the characters it sent (`requestChars`: system, messages and tool definitions, widen only). Admin usage shows characters per token by call site, so the budgets can be set from measurement.
2. **Count before the large requests.** For an Anthropic request whose estimate passes 50 percent of the model's context window (from the model catalog, as `modelOutputCap` reads the output limit), the client calls `messages.countTokens` with the same model, system, messages and tools before sending. When the count plus the answer's room is over the context window, the request is not sent: the caller gets a named error (`REQUEST_TOO_LARGE`, with the counted and allowed sizes), and the callers that build evidence (drafting, analysis, the Brief, chat) rebuild once with their character budget scaled by the counted ratio, then count again. Smaller requests are not counted (no added wait). OpenRouter models are not counted (no endpoint); they keep the estimate.
3. **No change to what is sent** when the estimate was right: the requests of every existing test stay byte for byte.

**Tests.** The SDK boundary with `fetch` stubbed: a large request counted first and sent; one counted over the window rebuilt smaller and sent; one still over after the rebuild refused by name; a small request not counted; an OpenRouter request not counted; `requestChars` on the usage row.

## F2. Project copies in batches

**Today.** Duplicating a project (`projectDuplication.copyProjectContentBetween`) creates every destination row in one mutation (`projects.prepareProjectContentCopy`, `copyProjectInputRows`): up to 250 files with their whole text, the evidence rows and the report. A project with many large files passes a mutation's read or write limit, and the copy fails.

**Change.**
1. The first mutation creates the destination file rows without their text, marked `textCopyPending` (widen only), plus the transcripts, evidence and report as today.
2. The action then copies each file's text in its own mutation, in order (one file, or the pieces of one large file in pages), and clears the mark. Original bytes are cloned as today.
3. A file still marked is not read by drafting, chat or search (it is "still copying" in the file list), and the start dialog says the copy is not finished. A copy that stopped part way is resumed by the same action when the writer opens the project (idempotent per file), and the duplicate wizard shows the files still copying.

**Tests.** A copy of 60 files of 400,000 characters under the transaction limits; a copy stopped after file 10 and resumed; a pending file left out of drafting and search; the receipt unchanged.
