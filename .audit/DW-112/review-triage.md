# DW-112 review triage rationale

The four owning-workflow reviewers examined the source/test/spec diff bound by `review-input.diff`. Edge Case Hunter returned no findings, Verification Gap returned no findings, and the remaining eleven unique suggestions or surface observations were rejected for the reasons below. No deferred item was added because none was both a verified pre-existing defect and material enough for later focused work.

1. **Post-model adoption is recorded as `derived`** (medium, reject). The stage did run the model and derive candidates before publication discovered the concurrent winner. `reused` remains the no-model-call branch at `convex/ai/brief.ts:450-460`; changing the outcome taxonomy is a separate observability contract outside the bundle's persistence-only intent. The persisted Brief id and uniqueness behavior remain correct.
2. **Creation ordering versus historical duplicate version numbers** (medium, reject). `latestBriefForInputs` preserves the exact pre-existing `findReusableBrief` query at baseline. DW-112 prevents new first-version duplicates; it does not define migration or repair semantics for hypothetical historical duplicates, and no deployed duplicate fixture was established.
3. **Generation and project mismatch on the internal mutation** (medium, reject). The mutation already accepted and patched `generationId` separately from `projectId` before this change, and its only production caller supplies both from one `BriefStageArgs`. The new branch does not create a public trust boundary or broaden caller authority.
4. **Adoption cannot run after an arbitrary baseline-read failure** (low, reject). The bundle requires an in-transaction recheck at persistence, not recovery from unrelated database failures before persistence is reached. The fail-open stage contract intentionally permits no Brief after such a failure.
5. **`convex-test` serializes top-level mutations** (medium, reject). This limitation is disclosed in the spec's residual risks. The regression synchronizes two callers after both reuse misses and before real registered mutations. Its baseline control produced two Brief ids, while the fixed source produced one row and two stamps. Production conflict retry is a Convex transaction guarantee, not an application branch simulated by this harness.
6. **Winning payload consistency is not asserted field by field** (low, reject). Convex commits the parent, entries, and winning generation stamp in one mutation. The test asserts one parent id, one child row under that id, equal return ids, and both generation stamps. A mixed payload cannot be constructed by the changed branch without violating transaction atomicity.
7. **The adopt path does not instrument source reads** (low, reject). The acceptance surface is state: it returns and stamps the latest same-key Brief while parent and child table snapshots remain byte-for-byte equal. Read-count instrumentation would test an internal performance detail; source order already places adoption before candidate processing.
8. **No new cross-project same-hash case** (low, reject). Both the unchanged index definition and shared query constrain `projectId` before `inputsHash`; the refactor preserved those exact predicates. No changed branch omits the project component.
9. **Writer edit interleaving can move authority to version 2** (low, reject). The bundle describes two concurrent first derivations, not a human edit interleaving. Immutable historical generation links may legitimately differ after a later edit; each transaction adopts the latest same-key row visible when it runs.
10. **The review diff did not yet link final receipts** (low, reject). This was a review-timing observation. Workflow finalization subsequently added exact source hashes, the red control, complete parent receipts, reviewer hashes, and the implementation commit to `.audit/DW-112/evidence.md` and `## Auto Run Result`.
11. **Changed-input diff fixtures supply hashes directly** (low, reject). These tests isolate publication and diff behavior at the mutation boundary. The separate `briefInputsHash` tests cover evidence-to-hash derivation; DW-112 changes no hash-generation code.

The intent-alignment auditor's other observations deduplicate into items 5, 9, 10, and 11: higher pipeline entry, serialized transaction execution, writer-edit follow-through, workflow evidence outside the review diff, and supplied changed-input hashes. The original bundle explicitly locates the fix at `persistDerivedBrief` and asks for an in-transaction recheck, so the publication-boundary reading is selected without an unresolved intent gap.
